**نطاق التدقيق:** الهيكل، الملفات والأكواد والوثائق والـCI والمهام وسجلات المصدر والنماذج المجمدة. لا يشمل تدقيقًا مستقلًا مكتملًا لكل سطر من كود المنبع، أو اختبارًا على عتاد المالك/MT5، أو تقييم بيانات سوق/ربحية غير موجودة.

## الخلاصة التنفيذية

- مستودع خاص، 584 ملفًا مؤرشفًا من TradingAgents (213) وAurum (250) وMidas (121)، مع سجلات SHA وسلامة. يوجد 48 Issue مفتوحًا، كلها غير مغلقة؛ و59 اختبار وحدة/سلامة ناجح في GitHub Actions.
- **لا يوجد حتى الآن** نموذج مدرب على XAUUSD، مجموعة بيانات وسيط مدققة، تشغيل LLM محلي مثبت، Backtest خاص بمشروعنا، أو جسر تنفيذ MT5. نسخ المستودعات الخارجية لا تعني دمجها أو اختبارها تشغيليًا.
- حماية فرع `main` غير مفعّلة في واجهة GitHub وقت المراجعة (`protected=false`).
- تجميد كود المنبع جيد، لكن **اعتماديات Python وActions ليست مثبتة بالكامل**: `pyproject.toml` به نطاقات إصدارات، وCI يثبتها في كل تشغيل. كما لم يُنشأ SBOM وتدقيق أمني شامل.
- تحذير قوي: [نتائج Aurum الرسمية](https://github.com/zero-was-here/tradingbot/blob/39c33b49237e0f290f89bda18e27aa4e75021c03/docs/RESULTS.md) غير كافية لإثبات ميزة تداول. في قسم Walk-Forward كان Sharpe للمزيج `trend_core` = −0.17 قبل فترة Holdout. لا تستخدم الاستراتيجيات المستوردة باعتبارها رابحة.
- أي ربط حساب حقيقي يجب أن يظل **غير متاح** حتى اجتياز بوابات البيانات/النموذج/التنفيذ/الأمن/الوسيط والتحقق المستقل.

## أربعة تصحيحات برمجية ينبغي اختبارها قبل أي تطوير تنفيذ

### RISK-01 — شبكة أحجام اللوت عند الحد الأعلى

في `src/goldintel/risk.py`:

```python
increments = ((raw_lots - volume_min) / volume_step).to_integral_value(rounding=ROUND_FLOOR)
lots = min(volume_min + increments * volume_step, volume_max)
```

إذا كان `volume_min=0.01` و`volume_step=0.01` و`volume_max=0.025`، قد يختار `0.025` غير المتوافق مع الشبكة. يجب رفض مواصفات غير متسقة أو حساب أكبر نقطة على الشبكة لا تتجاوز الحد الأعلى. اختبر broker min/max/step مع أحجام كسور مختلفة؛ الاستنتاج في هذا المثال مستمد من قراءة الكود، وليس من حادثة لدى وسيط.

### RISK-02 — حدود نسب المخاطرة وتزامن الطلبات

التحقق الحالي يفرض الإيجابية فقط على `max_risk_fraction` و`max_daily_loss_fraction`، ولا يفرض مجالًا معتمدًا `0 < fraction <= 1` أو سقفًا تجريبيًا مناسبًا للحساب. `AccountState.open_positions` مجرد عداد ولا يحجز مخاطرة الأوامر المعلقة أو الطلبات المتزامنة. يجب بناء دفتر `RiskReservations` ذري باحتساب كل المراكز/الأوامر ذات الصلة وإلغاء الحجز عند استلام الحالة الموثقة من الوسيط.

### RISK-03 — حساب خسارة الوسيط والتكاليف الفعلية

القيمة `broker_order_check_ok` Boolean من المستدعي؛ ليست دليلاً قائمًا بذاته على استدعاء OrderCheck للطلب الحالي. الاعتماد على TickValue واحدة لا يغني عن مطابقة `order_calc_profit` أو `OrderCalcProfit` ومواصفات الرمز وتحويل العملة. يشمل التحقق gaps والانزلاق والعمولة والسواب والهامش عند تقدير Worst-Case Loss.

### RISK-04 — سلاسل حالة التنفيذ

لا يوجد Execution Ledger أو FSM تنفيذي فعلي يميز pending/sent/unknown/filled/partial/rejected/reconciled. يجب تنفيذ idempotency على مستوى التخزين والوسيط، والتوقف عن إعادة المحاولة عند نتيجة غامضة حتى تحقق المطابقة.

## اكتشافان معماريان إضافيان

**عزل المنبع:** الأرشيف يحمل 584 ملفًا، لكنه ليس حزمة واحدة قابلة للاستيراد أو التشغيل المتكامل. هناك تداخل بين Midas وTradingAgents (14 ملفًا بنفس المسار وبصمة Git blob، نحو 3.74MB من الموارد المتطابقة)، لذا يجب اختيار مصدر لكل وحدة وعدم إدراج الاثنين في Python import path دون namespace/adapters صريحة.

**تكلفة الوكلاء:** أعضاء مجلس Bull/Bear الذين يستخدمون الأوزان نفسها ليسوا «أدلة إحصائية مستقلة». يجب تقييم أثرهم في معايرة القرار وعائده الحقيقي مقارنة بنفس النظام الكمي من دون LLM، وكذلك الكمون والهلوسة؛ إذا لم يضف مجلس الوكلاء قيمة، يبقى مساعدًا للتفسير لا للتداول.

## اكتشافات بيانات الذهب التي لا تحتمل التساهل

1. CFD/OTC لدى الوسيط ≠ سعر سوق عالمي قابل للتنفيذ: `XAUUSD` له رمز ومواصفات ومناطق توقيت وسبريد وجلسات وعمولات مختلفة حسب الوسيط.
2. سجل `Tick/Bid/Ask` وحالات عبور وقف/هدف داخل الشمعة ضروري لتقييم نموذج المتاجرة M5/M15؛ التنبؤ بالـClose ليس Backtest.
3. اندماج بيانات M15/H1/H4 والأحداث الاقتصادية يجب أن يعتمد على آخر شمعة **مكتملة** ووقت النشر الفعلي، مع سياسة DST وانقطاع الجلسات؛ لا يجوز استخدام `bar_open` كوقت معرفة نتيجة الشمعة.
4. بيانات الذهب الآجلة GC ومراكز CFTC والعوائد الحقيقية والدولار قد تستخدم **كخصائص تفسيرية** للذهب فقط؛ لا تعني توسيع التداول إلى أصول أخرى. تطبيع basis/roll/settlement إلزامي عند المقارنة مع XAUUSD CFD.
5. لا تنشر تاريخ الأسعار أو بيانات الوسيط على GitHub دون رخصة وحقوق واضحة؛ احفظ بيانات التدريب كأصل منفصل ببصمة محققة.

## خارطة تحسين الخوارزميات — وفق القيمة المتوقعة لا الضجيج

### الطبقة الأولى: إثبات أفضلية أساسية
- Baselines: always-NO_TRADE، نموذج عدم تغير السعر، momentum بسيط، استراتيجية جلسات ثابتة، ثم LightGBM وCatBoost.
- هدف موجه للتنفيذ: `P(TP before SL | state)` و`P(SL before TP | state)`، مع حساسية لأفق الاحتفاظ، وBrier/LogLoss/Calibration.
- نموذج `NO_TRADE` مستقل يرفض الإشارات عندما لا توجد قيمة متوقعة موجبة بعد السبريد والانزلاق/العمولات. أحيانًا تقليل الصفقات أهم من تحسين Accuracy.
- امتناع بناءً على عدم اليقين؛ تجارب معايرة متتابعة وقواعد فشل واضحة.

### الطبقة الثانية: نماذج البحث المحسنة
- تحليل أنظمة السوق: `trend/range/high-vol/illiquid/news` باستخدام خصائص متاحة عند القرار، مع `regime-gated` ensemble، لا HMM مكشوف المستقبل.
- `CUSUM` أو event sampling لتقليل عينات متلاصقة؛ Triple-Barrier مرتبطة بتكلفة واقعية وATR/volatility؛ sample uniqueness weights عند الحاجة.
- `Quantile` forecasts من Chronos-2/NHITS، ومقارنة calibration وكثافة ذيول الحركة؛ تقييم Conformal intervals بحذر لأن اعتماد الضمانات العادية يفشل تحت عدم الاستقرار الزمني.
- تمييز التحسن الحقيقي عبر عزل كل مكوّن: price-only مقابل price+macro، baseline مقابل Chronos، quant-only مقابل quant+agents. يجب أن تُسجّل **كل المحاولات** لحساب تحيز الاختيار، وبروتوكولات DSR/PBO وWalk-Forward وholdout المقفل.

### الطبقة الثالثة: بحث عالي التكلفة ومشروط
- تحسين execution/SL/exit timing على محاكي بيانات Tick مع تأخير متغير وspread شرطي (بعد تحقيق Data Gate).
- تعلم معزز فقط إن نجحت مطابقة Backtest ↔ paper/execution؛ عدم السماح للمكافأة بتحفيز التلاعب بالمحاكي أو زيادة المخاطر.
- نماذج سوق متقدمة وشبكات زمنية ضخمة *اختيارية*. لا تنتقل للمرحلة الأثقل دون تفوق متكرر واضح على baseline بسيط.

## القرارات والنتائج التي لا ينبغي تضخيمها

تقرير Aurum الخارجي لم يجد أفضلية مقنعة في معظم اختبارات OOS السابقة؛ أظهر `trend_core` Sharpe −0.17 أثناء Walk-Forward، ثم Sharpe 1.34 في holdout مع فاصل ثقة واسع يتضمن الصفر. **هذه ليست نتائج مشروعنا** ولا إثباتًا لأن استراتيجياته رابحة؛ هي سبب إضافي لتسجيل جميع الاختبارات وعدم استنتاج الربحية من فترة ناجحة منفردة.

## خارطة الأدلة المطلوبة (Gates)

**G0 الحوكمة:** protected main + CI مطلوب + بيئة pinned + SBOM + سجل مخاطر/قرارات محدث.  
**G1 البيانات:** لقطة بروكر فعلية، tick/bid/ask، timezone verified، rights، فجوات وتقويم سوق، مصدر مستقل للمطابقة.  
**G2 البحث:** Experiments ذات معرفات وصور بيانات ثابتة، baselines، labels غير مسربة، Purged WFV، Holdout locked.  
**G3 الاقتصاد:** محاكي Event-Driven بعمولات/سبريد/هامش/انزلاق ودفتر محاولات وفواصل ثقة، إجمالي عائد إيجابي مثبت نسبيًا قبل وبعد Stress.  
**G4 الوكلاء:** Inference محلي، JSON validation، أدوات read-only، injection tests، قياس قيمة إضافية مقابل Quant-only.  
**G5 التنفيذ:** MT5 Demo بقرار بشري، reconciliation، idempotency، circuit breakers، اختبارات الشبكة والفشل.  
**G6 الإنتاج:** مراجعة مستقلة، Runbook، نسخ احتياطي واسترجاع مجرب، مراجعة شروط وسيط وتنظيم، موافقة بشرية منفصلة؛ لا نشر حقيقي آلي.

**مبدأ الجودة:** لا تقدم إلى المرحلة التالية اعتمادًا على عدد ملفات أو عدد اختبارات برمجية، بل على أدلة محددة قابلة لإعادة الإنتاج وإعادة التدقيق.
